# Как собрать

Окружение: WSL Ubuntu 24.04, 28 логических ядер, 48 ГБ ОЗУ, около 300 ГБ
свободного места на nvme. На меньшем железе тоже соберётся, просто дольше.

## 1. Дерево

    gh repo clone mamaich/GammaOSNext-RG52mini
    cd GammaOSNext-RG52mini

Это монорепозиторий: всё дерево AOSP в одном git, около 26 ГБ в `.git` и
1.2 млн файлов в рабочей копии. `repo sync` не нужен.

**Внимание на git-lfs.** Фильтр LFS обычно зарегистрирован системно, и обычный
checkout начнёт разворачивать `.repo/project-objects/**/*.pack` — пакфайлы
исходных репозиториев LineageOS, для сборки бесполезные. Правильно так:

    git config lfs.fetchexclude ".repo/**,vendor/gapps/**"
    git config lfs.concurrenttransfers 16
    GIT_LFS_SKIP_SMUDGE=1 git reset --hard HEAD
    git lfs pull --exclude=".repo,vendor/gapps"

Полезного LFS — 256 файлов на 24.6 ГБ, и без них сборка не стартует: там
`prebuilts/clang/host` (5.6 ГБ), `prebuilts/misc/common` (2.0),
`prebuilts/rust/linux-x86` (1.6), `prebuilts/jdk` (2.0), `prebuilts/sdk` (1.4).
GApps нужны только для целей `*g*` — тогда `git lfs pull --include="vendor/gapps"`.

Проверка, что ничего не осталось указателем:

    git lfs ls-files | awk '$2=="-"{print $3}' | grep -vE '^\.repo/|^vendor/gapps/'

        g++-multilib gcc-multilib gnupg gperf imagemagick lib32ncurses-dev \
        lib32readline-dev lib32z1-dev libelf-dev liblz4-tool libncurses-dev \

        schedtool squashfs-tools xsltproc zip zlib1g-dev python3 \

    export CCACHE_DIR=~/rg52/gamma/ccache
    ccache -M 100G && ccache -o compression=true -o compression_level=1

## 3. Сборка

Перед первой сборкой надо скачать apk microG: в репозитории их нет, потому что
GmsCore весит 103 МБ.

    device/rg52mini/microg/fetch.sh

Версии и контрольные суммы в скрипте зафиксированы, так что сборка
воспроизводима. Без этого шага сборка упадёт на копировании отсутствующих
файлов.

    export USE_CCACHE=1 CCACHE_EXEC=/usr/bin/ccache CCACHE_DIR=~/rg52/gamma/ccache
    bash buildtv_cc.sh nosync

### VNDK: искать в `/system_ext/apex`, а не в `/system/apex`

Снимки VNDK для старых vendor приезжают в образ сами: `gsi_release.mk` просит
`PRODUCT_EXTRA_VNDK_VERSIONS := 30 31 32 33 34`, а `lineage_tv_arm64_bvN.mk`
добавляет `28 29`. Апексы `com.android.vndk.v*` ставятся в
**`/system/system_ext/apex/`** — около 486 МБ, из них
`com.android.vndk.v33.apex` весит 47 МБ.

Знать это важно, потому что признаки легко прочитать наоборот. В конфигурации
выпуска `ap2a` (`build/release/build_config/ap2a.scl`) стоит
`RELEASE_DEPRECATE_VNDK = True`, отчего `envsetup.mk` берёт
`KEEP_VNDK ?= false`, `config.mk` обнуляет `BOARD_VNDK_VERSION`, а каталоги
`/system/lib64/vndk-*` остаются пустыми. По этим трём приметам напрашивается
вывод, что VNDK в образе нет. Он есть — просто не там, где его ищут.

Почему для RG52 Mini это жизненно важно: раздел vendor **не носит своих копий**
`libhidlbase.so`, `libutils.so`, `libcutils.so`, `libc++.so`, `libbase.so`,
`libhardware.so` — в `/vendor/lib64` (149 файлов) их нет вовсе, всё приходит из
`/apex/com.android.vndk.v33`, который в Android 13 отдавал раздел system.

### `KEEP_VNDK=true` ставить нельзя — устройство не загрузится

Соблазн есть: переменная добавляет в образ 28 библиотек (`libssl.so`,
`libcurl.so`, `libminijail.so`, `libaudioroute.so`, `libwifi-system-iface.so`,
`android.hardware.soundtrigger@2.0.so` и подобные) и на первый взгляд ничего не
убирает. Но вместе с ними срабатывает `build/make/core/main.mk:357`:

    ifeq ($(KEEP_VNDK)|$(PRODUCT_PRODUCT_VNDK_VERSION),true|current)
    ADDITIONAL_PRODUCT_PROPERTIES += ro.product.vndk.version=$(PLATFORM_VNDK_VERSION)

В этом дереве `PLATFORM_VNDK_VERSION` равен **35**, а снимков дальше `v34` не
существует. В `/product/etc/build.prop` попадает `ro.product.vndk.version=35`,
после чего `linkerconfig` идёт за `/apex/com.android.vndk.v35`:

    linkerconfig: Unable to access VNDK APEX at path: /apex/com.android.vndk.v35
    linkerconfig: Check failed: !"undefined var" SANITIZER_DEFAULT_PRODUCT is not defined
    linkerconfig: linkerconfig terminated by signal 6

Механика в `system/linkerconfig/generator/variableloader.cc`: не найдя апекс,
`LoadVndkLibraryListVariables()` выходит **до** того, как определит
`SANITIZER_DEFAULT_PRODUCT`, а затем `contents/namespace/productdefault.cc`
обращается к этой переменной и роняет процесс.

Дальше рушится всё: `perform_apex_config` сообщает «failed to execute
linkerconfig», `/linkerconfig/ld.config.txt` не создаётся, и ни один процесс,
которому нужны отдельные пространства имён, не стартует. На устройстве это
выглядит как бесконечный перезапуск `vendor.gralloc-4-0`, отсутствие
`surfaceflinger` и чёрный экран после логотипа.

Проверено сравнением: в сборке по умолчанию `ro.product.vndk.version` нет
вообще, а `com.android.vndk.v33.apex` в обоих образах побайтно один и тот же.

Заодно: забрать апекс с работающего Android 13 всё равно нельзя — у Rockchip он
«плоский», то есть каталог `/system/apex/com.android.vndk.current/` вместо
файла `.apex`, а Android 14 плоские апексы больше не поддерживает.

Именно `buildtv_cc.sh`, а не `buildtv.sh`: он выставляет `GAMMAOS_BOOT_GC=cc`,
и boot-образ ART собирается под read-barrier CC. В ядре RG52 Mini
`CONFIG_USERFAULTFD` выключен, поэтому ART выберет CC; собранный под uffd
boot-образ на таком ядре заставляет перекомпилировать весь boot classpath
(~15 с) при **каждой** загрузке.

Скрипт делает `lunch lineage_tv_arm64_bvN-ap2a-userdebug`, `make installclean`
и `make systemimage`, после чего кладёт результат в
`out/home/build-output/lineage-21.0-<дата>-UNOFFICIAL-tv_arm64_bvN.img`.

Проверить, что окружение живо, можно и без LFS:

    source build/envsetup.sh
    source vendor/lineage/vars/aosp_target_release
    lunch lineage_tv_arm64_bvN-$aosp_target_release-userdebug

Ожидаемый ответ: `PLATFORM_VERSION=14`, `BUILD_ID=AP2A.240905.003`,
`PRODUCT_IS_ATV=true`.

Сборку можно прерывать: ninja продолжает с места обрыва, остальное добирает
ccache.

Одна строка — чтобы её было легко переносить при обновлении апстрима.

### Про свойства и порядок загрузки

`system/core/init/property_service.cpp`, `PropertyLoadBootDefaults()`: свойства
собираются в отображение, и **чем специфичнее раздел, тем выше приоритет** —
значение из более позднего файла перекрывает более раннее. Порядок:
ramdisk → `system` → `system_ext` → `vendor` → `odm` → `product`.

Отсюда два следствия:

* `ro.sf.lcd_density` в vendor равен 186, а рабочее значение 213. Перебить его
  из `system` невозможно, нужен `PRODUCT_PRODUCT_PROPERTIES` (то есть
  `/product/etc/build.prop`). Ровно так это было сделано и в Android 13.
* `ro.config.low_ram` ATV-база GammaOS ставит в `true` через
  `PRODUCT_VENDOR_PROPERTIES`; в GSI-сборке раздела vendor нет, так что в образ
  это не попадает, но на всякий случай `false` прописан явно в product.

## 5. Образ SD-карты

    bash device/rg52mini/tools/mk-sdimg.sh [system.img] [выход.img]

Скрипт собирает полный образ:

| Что | Откуда |
|---|---|
| сектора 0…237567 | побайтно из рабочего образа Android 13: защитный MBR, GPT, idbloader (`RKNS` с сектора 64), `resource` и загрузочный FAT |
| `uboot` (p1) | **своя сборка u-boot**, поверх скопированного |
| `Image` в FAT | **своя сборка ядра**, поверх скопированного |
| `system` (p4) | собранный GSI, раздел **постоянного размера 3400 МиБ** (ниже, зачем) |
| `vendor` (p5) | побайтно оттуда же, с правками (ниже) |
| `cache`, `metadata` | пустые ext4 |
| `misc` | нули |
| `userdata` | пустой: отформатирует init, затем `rg52-resize` растянет на всю карту |

Имена разделов обязаны совпадать с оригиналом — fstab обращается к ним через
`/dev/block/by-name`.

Кроме заливки разделов скрипт правит vendor: убирает лаунчер Android 13 с его
сторожем целостности и обе службы Flydigi, а `/vendor/bin/rgp2pad` подменяет
своей сборкой. Зачем именно — в [02-план.md](02-план.md).

### Раздел `system` постоянного размера, и менять его нельзя

    SYS_SECTORS=6963200              # 3400 МиБ

Раньше размер считался от содержимого плюс мегабайт запаса, и это однажды стоило
незагружаемой карты. Обновление по воздуху пишет в раздел **целую файловую
систему**; если раздел на карте окажется меньше её хоть на блок, ext4 отказывает,
`init` не может смонтировать `/system`, уходит в `InitFatalReboot`, и устройство
попадает в петлю загрузчика, из которой выводит только перезапись карты. Полный
разбор — в [02-план.md](02-план.md).

Постоянное число означает, что разметка у всех сборок одна и любое обновление в
неё войдёт. Запас при текущем `system.img` — 349 МБ. Скрипт печатает его при
каждой сборке:

    раздел system: 3400 МиБ постоянно, запас 349 МиБ

Если сборка перестанет влезать, скрипт останавливается с объяснением. Увеличивать
`SYS_SECTORS` можно, но это **меняет разметку**: обновление по воздуху на карты,
записанные прежними образами, после этого не встанет — им понадобится перезапись.
Поэтому число трогается только вместе с осознанным отказом от обновления для
прежних версий.

Файловая система внутри раздела по-прежнему по содержимому, и так и надо: ФС
меньше раздела монтируется без разговоров, больше — нет.

### Ядро и модули берутся из своей сборки, и это важно

Загрузочный FAT и `vendor` копируются из эталонного образа побайтно, поэтому в
них лежит ядро того поколения, когда эталон делали. Пока ядро не менялось, это
было незаметно. Как только в ядре появился `CONFIG_USERFAULTFD`, оно стало
ловушкой, причём двойной и молчаливой:

* **Ядро.** Система собирается под уплотняющий сборщик мусора
  (`ro.dalvik.vm.enable_uffd_gc=true`), и загрузочный образ скомпилирован под
  него же. Старое ядро без `CONFIG_USERFAULTFD` заставит ART откатиться на
  копирующий сборщик, это разойдётся с загрузочным образом, и `boot classpath`
  будет пересобираться через dex2oat при каждой холодной загрузке.
* **Модули Wi-Fi.** `CONFIG_USERFAULTFD` меняет разметку `struct
  vm_area_struct`, а ядро собрано с `modversions`. Старые `aic8800_bsp.ko` и
  `aic8800_fdrv.ko` с новым ядром не загрузятся вовсе — на свежей установке не
  будет ни Wi-Fi, ни Bluetooth. Здесь легко обмануться: `vermagic` у старого и
  нового модуля **совпадает**, потому что версия ядра та же, а расходятся
  контрольные суммы символов.
* **Модуль `rk915.ko` — то же самое, и его особенно легко забыть.** Платы ранней
  ревизии несут чип RK915 вместо AIC8800D80, оба на одном слоте SDIO и с общим
  выводом питания, поэтому драйвер выбирается по факту железа: сперва rk915 из
  `init.insmod.cfg`, и только если интерфейс не появился — aic8800 из
  `/vendor/bin/wifi_pick.sh`. Незагружаемый `rk915.ko` ломает этот выбор молча:
  на ранней плате Wi-Fi пропадает совсем, а на поздней всё выглядит штатно,
  потому что отказ rk915 там и есть норма. Разбор — в
  [02-план.md](02-план.md).

Поэтому скрипт подменяет и то и другое из каталога своей сборки:

    KERNELDIR=${KERNELDIR:-/home/mamaich/rg52/out-kernel-uffd}

Оттуда берутся `Image`, оба `aic8800_*.ko` и `rk915.ko`. Если файлов нет, скрипт
не подставляет эталонные молча, а громко предупреждает — тихая подстановка здесь
опаснее отсутствия.

С `rk915.ko` скрипт сборки ядра снимает отладочные символы (1,4 МБ против
412 КБ): раздел vendor заполнен на 98 %, свободно порядка 7 МБ. Это то же, что
делает ядро при `INSTALL_MOD_STRIP=1`. Модули aic8800 оставлены как есть,
проверенными, но при нужде там есть ещё около 2,5 МБ.

DTB намеренно остаётся из эталона: `dts` мы не меняли, и проверена на
устройстве именно пара «новое ядро + прежний dtb».

Собирается всё это скриптом `device/rg52mini/tools/build-kernel-uffd.sh` —
он кладёт `Image`, DTB и модули в `KERNELDIR` одним проходом, чтобы ядро и
модули заведомо совпадали по `vermagic` и контрольным суммам символов.

### Скрипт выбора Wi-Fi тоже подменяется

    WPICK=${WPICK:-$TREE/device/rg52mini/wifi_pick.sh}

`/vendor/bin/wifi_pick.sh` в эталоне есть, но он ждёт появления интерфейса
**вслепую** — четыре секунды на любой плате. На ревизии B, то есть у
большинства, эти секунды не бесплатны: прошивка AIC8800 поднимается ещё около
девяти секунд после `insmod`, а Android начинает подключаться, как только видит
`wlan0`. Ожидание сдвигало готовность прошивки ровно в тот момент, когда каркас
уже пробует связаться с точкой доступа, и попытка отбивалась изнутри драйвера:

    CTRL-EVENT-ASSOC-REJECT bssid=00:00:00:00:00:00 status_code=30

После кода 30 Android ждёт до следующей попытки пять минут — столько устройство
и оставалось без сети после каждой загрузки.

Наш вариант ждёт только тогда, когда есть чего ждать: если `rk915` не значится в
`/proc/modules`, его инициализация провалилась (на ревизии B так и происходит),
интерфейса от него не будет никогда, и AIC8800 грузится сразу. Служба занимает
2,3 секунды вместо 8,1, запас до попытки подключения — двадцать семь секунд
вместо минус одной.

Если файла нет, скрипт сборки предупреждает и оставляет эталонный: с ним Wi-Fi
работает, просто поднимается на пять минут позже.

### Загрузчик — та же ловушка, что и ядро

Голова эталонного образа уже содержит наш u-boot: дамп `mmcblk1p1` с работающего
устройства содержит наш патч про HUSB311. Но она **заморожена** — всё, что
попадает в u-boot после того, как эталон был сделан, в образ само не приезжает.
Поэтому `uboot.img` тоже пишется из своей сборки:

    UBOOTDIR=${UBOOTDIR:-/home/mamaich/rg52/u-boot-rg52}

Раздел `p1` — это ровно `uboot.img`, FIT с u-boot и trust, и его 4 МиБ сходятся
в обрез, поэтому скрипт сперва сверяет размер с размером раздела и при
несовпадении оставляет эталонный загрузчик, сказав об этом вслух.

Собирается он штатным `./make.sh rk3562-rg52mini` в дереве u-boot. Скрипт ждёт
кросс-компилятор по пути `../prebuilts/gcc/linux-x86/aarch64/gcc-arm-10.3-2021.07-x86_64-aarch64-none-linux-gnu/bin/`,
так что достаточно сделать туда ссылку на тот же `arm-gnu-toolchain`, которым
собирается ядро.

idbloader (`RKNS` с сектора 64) намеренно остаётся из эталона: там SPL и блоб
инициализации DDR, а их мы не меняли. Если когда-нибудь тронем SPL или частоту
памяти — придётся добавить и его.

### Драйвер Mali тоже подменяется

`MALIDIR` (по умолчанию `out-mali-g25p0`) — каталог с `lib64/` и `lib/`, в
каждом `libGLES_mali.so` и две библиотеки AIDL
(`android.hardware.graphics.allocator-V2-ndk.so`,
`android.hardware.graphics.common-V4-ndk.so`).

В vendor от Android 13 лежит драйвер `g7p1-01bet0`, в котором две функции
резервируют по 192 КБ стека одним кадром; игры, дающие потоку отрисовки 128 КБ,
падают на нём с переполнением. Замена — `g25p0-00eac0`, ровно версия ядерной
половины драйвера в нашем ядре.

Взять его можно из Android-14 SDK для KickPi K3B: сайт производителя,
<https://www.kickpi.com/product/k3b/>, раздел Downloads. В дереве он лежит в
`vendor/rockchip/common/gpu/MaliG52_for_a53/lib{,64}/libGLES_mali.so` — вариант
`_for_a53` именно потому, что у RK3562 ядра Cortex-A53.

Библиотеки AIDL берутся из apex VNDK самой системы (`/apex/com.android.vndk.v34`):
версии совпадают, потому что GSI у нас Android 14. Обе разрядности
обязательны — с одними 64-битными система встаёт на `zygote_secondary`.

**И свойства ARM, без которых драйвер бесполезен.** Начиная с этой версии он
строит список конфигураций EGL не сам, а по свойствам
`ro.vendor.arm.egl.configs.*`, которые должен задавать vendor. В нашем от
Android 13 их нет, и драйвер остаётся без описания форматов: HWUI в каждом
приложении жалуется `Device claims wide gamut support, cannot find matching
config`, а Minecraft падает на старте. 56 строк лежат в
`device/rg52mini/mali-g25p0.prop`, взяты из того же Android 14 SDK, и скрипт
дописывает их в `/vendor/build.prop` — задавать `ro.vendor.*` может только
раздел vendor. Разбор — в [02-план.md](02-план.md).

Разбор — в [02-план.md](02-план.md).

Заодно переписывается `extlinux/extlinux.conf`: консоль ядра выводится на
uart0 (`ttyFIQ0`, 1500000 — узел `fiq-debugger` с `rockchip,serial-id = <0>`,
`earlycon=uart8250,mmio32,0xff210000`), поднимается уровень лога и добавляется
`androidboot.console=ttyFIQ0`, чтобы init поднял на этой консоли root-shell.
Для отладки первой загрузки это важнее скорости.
